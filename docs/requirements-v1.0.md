# Couple Ledger — 要件定義書 v1.0

**対象:** 2人用の割り勘・奢り・精算・約束管理アプリ  
**版:** 1.0 / **基準日:** 2026-11-13  
**ステータス:** 機能要件95項目は既決。残余の初期版実装細則は依頼により推奨値で確定。  
**対象プラットフォーム:** iOS / Android / Web  
**責任範囲:** ユーザー体験・振る舞い・セキュリティ・品質・受入条件を定義。DB/APIの実装は別工程。

> 本書は既決のFR-001〜FR-095を変更しない。既存の `001_initial_schema.sql` は **v0.1の未実行ドラフト**であり、本書の全条件への適合や本番導入可能性を保証しない。

## 0. サマリー

- **提供価値:** 2人の立替、奢り、約束、実際の送金を一つの記録にまとめ、誰が誰に何円支払うべきかを常に確認できる。
- **最重要原則:** 実際の支払い・送金の事実を原本とし、精算割当・相殺・前払いは再計算可能な派生情報とする。金銭を二重計上しない。
- **共有単位:** 1ペア2人。1人が同時に所属できるアクティブペアは最大1件。
- **初期版の範囲:** オンライン動作、JPYのみ。画像添付、定期登録、CSV出力、プッシュ通知、プロフィール写真、生体認証ロックは含めない。
- **開発構成:** Expo/React Native/Expo Router、Cloudflare Workers + Hono、Supabase Auth + PostgreSQL + Realtime。ホスティング・デプロイの詳細は設計工程で検証する。

## 1. プロダクトの境界

### 1.1 利用者と権限

| 利用者 | できること |
|---|---|
| 未認証 | アカウント登録、ログイン、メール確認、パスワード再設定。招待リンクを開いて認証へ進める。 |
| 認証済み・未連携 | 表示名設定、招待発行・参加、復活申請の確認、自分の設定変更。共有の支払い・精算・約束は作れない。 |
| 有効ペアのメンバー | ペア内の支払い・精算・約束の登録・編集・取消・復元・履歴閲覧。相手の承認は原則不要。 |
| アーカイブペアの元メンバー | 自分が所属した履歴の読み取り・検索。双方条件を満たせば復活を申請／承認できる。 |
| 退会済み | ログイン不可。残された相手のため共有履歴には匿名化されたペア内メンバー記録のみ残る。 |

### 1.2 対象外

- チャット、送金実行、銀行・決済サービス連携、支払い請求、督促。
- 複数通貨、為替換算、税計算、月次予算、統計ダッシュボード。
- 複数人グループ、複数の有効ペアの同時運用。
- オフラインデータ編集・保存、プッシュ通知。
- レシート画像、定期支払い、CSVエクスポート、プロフィール画像、生体認証ロック。

### 1.3 用語

- **支払い:** 実店舗等への支出を一人が記録すること。アプリ内の金銭送金とは区別。
- **割り勘:** 支払者以外のメンバーに指定負担額が発生する支払い。
- **奢り:** 支払者が相手に金銭負担を求めない支払い。約束が付いても金銭負担はゼロ。
- **精算:** メンバー間で実際に移動した金銭の記録。アプリ自体は送金しない。
- **自動相殺:** 相互の立替債務を等額減らす計算処理で、現実の送金は伴わない。
- **割当:** どの精算・相殺がどの支払いの負担を消化したかを示す計算結果。
- **前払い:** 現在の負担債務を超えて送金された未割当額で、将来の同方向の債務に充当する。
- **原本:** 支払い、精算、約束のユーザー操作で成立した記録。監査ログとは別。
- **現在のペア:** `active` 状態のペア。**過去のペア:** `archived` 状態のペア。

| FR-017 | 復活の双方同意 | 一方が申請し他方が承認。双方が他の有効ペアに所属していないこと。 |
| FR-018 | 約束の本文・担当変更 | ペア双方が承認不要で約束本文・担当者を編集可能。 |
| FR-019 | 奢り＋約束の種別変更 | 約束を伴わない種別へ変える際は確認し、紐付く約束を自動取消。履歴を保持。 |

| FR-038 | 精算登録の候補 | 入力送金額に応じて未精算支払いを古い順に選択・割当。ユーザーが修正可能。 |

### 4.2 正常系フロー

1. **新規利用:** メール＋パスワード登録→メール確認→表示名設定→招待リンク／コードを発行、または受信して参加→2人連携完了→共有ホーム。
2. **簡単な支払い:** 支払い追加→金額のみ入力→必要なら既定値を編集→登録→双方の画面へ同期。
3. **奢り＋約束:** 種別を選ぶ→相手の金銭負担を0円に設定→約束本文と任意期限を入力→担当を確認→登録。
4. **精算:** 送金方向を確認→額を入力／全額入力→対象の負担を選択・割当調整→実際の送金が済んだ事実として登録。
5. **解除・復活:** ペア解除を確認→履歴をアーカイブ→過去ペアから復活申請→相手の承認→元のペアを再開。
6. **退会:** パスワード再入力→共有履歴・未精算額・自由記述の扱いを確認→ペア自動アーカイブ→プロフィール・Auth削除→相手には匿名履歴を保持。

### 4.3 画面の検証・確認事項

- 支払い・精算の金額入力は数字のみ、0・負数・小数・範囲超過を拒否する。
- 金額や送金方向の変更では、差額プレビューを確認するまで更新不可。プレビューが古くなったら再生成。
- 約束の完了・取消はどちらも実行可能。期限の超過で状態や色を自動変更しない。
- アーカイブ画面では閲覧・検索のみ許可。復活申請は別操作として明確に表示。
- ロード中・成功・失敗・通信切断・競合・期限切れを区別して表示する。

## 5. 金銭ドメインと計算仕様

### 5.1 残高の定義

ペア作成時に固定した `slot=A/B` を用い、残高 `N` を **正なら「BがAに支払う」**、負なら **「AがBに支払う」** と定義する。

```text
N = Σ(有効なA支払い割り勘の相手負担額)
  - Σ(有効なB支払い割り勘の相手負担額)
  + Σ(有効なA→B実送金)
  - Σ(有効なB→A実送金)
```

- 奢りと取消記録は債務に含まない。実送金は金銭の事実として上式にのみ含める。
- **自動相殺・手動／自動割当・前払いの適用を、この残高式で再加算・再減算してはならない。**
- 個別支払いの「未精算／一部／精算済み」は割当計算の表示上の状態。全体残高の正否とは別。

### 5.2 決定的な割当の再計算

1. 有効な支払い・精算を取得し、ペア内トランザクションで更新を直列化する。
2. 有効な `settlement_targets`（ユーザーの希望）を優先し、対象債務／実送金の上限まで割当を確定する。
3. 残る正負の債務を、業務日付・登録時刻・IDの古い順に自動相殺する。**相殺は現金移動として扱わない。**
4. 余った各方向の実送金を、該当方向の残債務へ古い順に自動割当する。
5. なお余る送金は前払いとして方向別に保持し、将来の同方向の支払い負担へ自動充当する。
6. 計算結果の `settlement_allocations` / `offset_allocations` は置換可能な投影として保存する。実送金の原本は保持する。

**重要な制約:** ある支払いへの割当＋相殺合計は当該支払いの相手負担額を超えず、1つの送金からの割当合計は実送金額を超えない。手動希望額が無効化された場合は合法な範囲で縮小し、余剰だけを再配分する。送金と逆方向の債務へは直接割り当てない。

**時系列扱い:** 支払日・精算日を利用して順序を決めるが、バックデートされた編集にも対応するため、各再計算は「現在の全原本に対する整合する投影」を作る。画面上で過去時点のキャッシュを現在残高として誤表示しない。

### 5.3 代表例

| 操作 | A基準の残高 |
|---|---:|
| Aが2,000円支払い、B負担1,000円 | +1,000円 |
| Bが1,200円支払い、A負担600円 | +400円 |
| B→Aで700円実送金 | −300円 |
| Aが1,000円支払い、B負担500円 | +200円 |

- 2件目で600円が相殺される。3件目の700円のうち400円が債務へ充当され、300円が前払いとなる。4件目の新しい500円負担へ300円を充当し、差額200円が残る。
- **この一連の計算は全原本から再現できること**を受け入れ条件とする。

### 5.4 編集・取消・復元

- 変更前に `version` とペアの `ledger_revision` からプレビュー生成、確定時に再照合。
- 支払い取消で付随約束を自動取消。支払い復元後も約束は取消状態のまま。約束復元は親が有効な `gift_promise` の場合のみ。
- 精算の取消・復元は送金を「無効／有効」にする処理であり、現実の返金を自動的に発生させない。
- 過払いや負の残高はエラーではない。方向を明示し、「全額入力」は現時点のその利用者が負う純債務のみを埋める。

## 6. アカウント・ペアの状態遷移

### 6.1 アカウント

```text
未登録 → 登録（メール未確認） → メール確認済み
      → 表示名設定済み → 未連携／有効ペア／過去ペア所持
      → 退会処理 → 退会済み
```

- パスワード変更: 現パスワード認証、操作端末維持、他端末失効。
- パスワード再設定: 全端末を失効。既発行アクセストークンが即時失効しない認証方式の場合、短命JWTとサーバー側失効判定で実効時間を制限する。
- メール変更: 本人確認→新アドレス認証→更新。元のユーザーIDは維持。
- 標準ログアウト: 操作端末のみ。

### 6.2 ペア

```text
pending（招待待ち） → active（2人連携） → archived（解除）
                                 ↑                 │
                                 └──双方同意で復活──┘
```

- 参加確定時に、招待有効性・ユーザーが既に有効ペアにいないこと・同一人物ではないこと・人数を再検証する。
- 以前の同じ相手がいたら新規ペアを作らず復活フローへ進む。
- 削除済みユーザーのペアは復活不可。期限切れや拒否は申請状態でありペア状態ではない。
- ペア解除・復活・参加・退会が同時に走った場合も「1人につき有効ペア最大1」のDB不変条件を維持する。

### 6.3 招待と復活申請

- 招待は7日間・1ペア1件のみ有効。再発行時に旧招待を失効し、使用で消費。
- コードは見間違えやすい文字を除いた大文字英数字8文字。リンクのトークンは別の高エントロピー乱数。
- 参加はボタンで確定。未ログイン・未登録なら認証後に元の招待へ戻る。認証前後で再検証する。
- 復活申請は7日間有効で、承認待ちは最大1件。受信者は承認・拒否、申請者は取消可能。
- 拒否後の同じ申請者からの再申請は7日待機。取消・期限切れ・新ペア成立による無効化は即再申請可能（双方が未連携の場合）。
- 復活申請中に別の有効ペアが成立したら、申請を自動失効させる。

## 7. データモデルと整合性

### 7.1 原本・投影・セキュリティ境界

| 種別 | テーブル | 主な責務 |
|---|---|---|
| プロフィール | `profiles` | ユーザーIDと表示名 |
| ペア | `pairs`, `pair_members`, `active_pair_memberships` | ペア状態、A/B固定枠、唯一の有効所属 |
| 招待 | `pair_invites`, `pair_revival_requests` | トークン期限、承認待ち・拒否等 |
| 原本 | `expenses`, `settlements`, `promises` | 支払い・実送金・約束の現在有効な事実 |
| ユーザーの割当意図 | `settlement_targets` | 手動指定の対象・希望額 |
| 再計算結果 | `settlement_allocations`, `offset_allocations` | 実送金充当・自動相殺の派生情報 |
| 証跡 | `audit_logs` | 誰がいつ何を変更したか（前後値） |
| 制御 | `idempotency_keys` | 操作IDごとの二重実行防止 |

### 7.2 必要なDB不変条件

1. 1ペアのメンバー枠はA・Bのみ。`active`ペアには実在する2人がちょうど所属。
2. 1アカウントが2ペアで同時に有効所属しない。
3. 支払い・精算・約束の参照先は同じペア内に限定。自分自身への精算は不可。
4. 支払い金額は正の整数、相手負担額は0〜総額。奢りの金銭債務は0。
5. `gift_promise` の有効支払いには、関連約束がちょうど1件必要。
6. 支払いが取消／約束なし種別なら付随約束は完了・未完了であってはならず取消状態。
7. 同じ操作IDを再送しても原本作成は一回だけ。同じキーで異なる入力はエラー。
8. 変更前後の監査ログは追記のみ。削除者の識別情報は退会方針に従って取り扱う。
9. 有効なペアの更新はトランザクション境界で整合し、計算結果は原本と一致。

### 7.3 既存DB v0.1ドラフトとの関係

既存の `001_initial_schema.sql` は原本と投影の分離、14テーブル、RLS、残高ビューの骨格を備えている。一方、**PostgreSQL実機でのマイグレーション、権限・RLS、ペア状態遷移、精算投影の整合性テストは未完了**。この仕様書で「実装済み」とは扱わない。

## 8. API契約・エラー

### 8.1 API原則

- 認証済みアクセスはSupabase AuthのJWTで認証し、APIで対象ペア・ユーザー・操作権限を必ず検証。
- 金銭を変更する処理は、本人認可→バージョン確認→原本変更→割当再計算→監査ログ追記を1 DBトランザクションで完結。

| 200/201 | 取得・変更・新規登録成功 | 最新値で画面更新 |
| 400/422 | 入力や状態遷移の不正 | 具体的な入力・状態エラー |
| 401 | 未認証／期限切れ | ログイン・認証回復 |
| 403 | 権限なし | 拒否。相手のデータを漏らさない |
| 404 | 存在しない／アクセス不可 | 安全な未検出表示 |
| 409 | versionまたはrevisionの競合、同一冪等キーの内容不一致 | 最新値再取得、差分確認、再操作 |
| 410 | 招待・復活申請の期限切れ | 再発行／再申請を案内 |
| 429 | コード試行・ログインのレート制限 | 再試行可能時刻を表示 |
| 5xx/ネットワーク | 一時的障害 | 成否不明時は同じ冪等キーで照会・再試行 |

## 9. セキュリティ・プライバシー・退会

### 9.1 アクセス制御

- ペアの共有データは、そのペアに属する認証済みユーザーだけが閲覧可能。アーカイブ閲覧も同様。
- **RLSは防御層の一つであり、Honoの操作主体認可を省略できるものではない。** `service_role` 相当の権限ではRLSを回避できる場合がある。
- 招待の生トークン、パスワード、JWT、秘密鍵は監査ログ・アクセスログに記録しない。
- クライアントのセッション情報はOSの安全なストレージ等へ保存し、WebではXSS・CSRFのリスクを考慮して適切な保管方式を採る。
- 監査ログはユーザーから変更・削除不可。ただし退会・双方退会時の匿名化／削除はプライバシー処理として実施。

### 9.2 退会の仕様

- 現在のパスワードを再入力し、退会の影響と未精算残高・共有本文の取り扱いを確認する。
- 有効ペアは原子的にアーカイブし、残高と履歴は他方が閲覧可能なまま保持。
- 退会者の認証IDと表示名の結び付きを除去し、UIでは「退会済みユーザー」と表示。
- 支払い名・約束本文・監査の変更前後JSONなどに入力された個人名は自動的に完全消去できるとは限らない。**FR-081に従い原則として本文を保持する**ことを明示する。
- 両者が退会したら共有データを主DBから削除。バックアップ・障害ログでの残存は提供基盤の保管仕様と運用に従って最長期間を確定し、プライバシーポリシーに記載する。

### 9.3 運用上の個人情報ルール

- 本番運用前に、プライバシーポリシー・利用規約・問い合わせ先・退会説明を整備する。
- ログの個人情報・トークンは必要最小限とし、削除処理と連動したマスキング方針を設ける。
- 事故調査の監査証跡と、退会後の個人情報削除とのバランスを設計審査する。本文の任意PII自動削除を**保証したと表現しない**。
